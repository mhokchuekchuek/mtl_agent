# SQLJudge Design Decision

## Context

We need to evaluate whether the SQL queries generated by the agent are correct.

## Options Considered

### Option A: Code-based comparison (execute and compare results)

```
1. Execute generated SQL
2. Execute expected SQL
3. Compare row counts and content
```

**Pros:**
- Fast, deterministic
- No LLM cost

**Cons:**
- Can't handle semantic equivalence (e.g., `ORDER BY` difference when order doesn't matter)
- Requires database connection during evaluation

### Option B: LLM compares SQL queries (no execution)

```
1. Send generated SQL + expected SQL + schema to LLM
2. LLM evaluates semantic equivalence and syntax
```

**Pros:**
- Understands semantic equivalence
- No database connection needed
- Handles edge cases (different syntax, same result)

**Cons:**
- Slower, costs money
- Non-deterministic

### Option C: LLM compares execution results

```
1. Execute both queries
2. Send results to LLM for comparison
```

**Pros:**
- Most accurate

**Cons:**
- Slowest, most expensive
- Requires database connection

## Decision

**Option B: LLM compares SQL queries (no execution)**

## Rationale

1. Semantic equivalence matters - `SELECT * FROM Products WHERE price < 100` and `SELECT * FROM Products WHERE price < 100 ORDER BY price` return same data
2. Supports negative test cases - LLM can evaluate "correctly avoided generating SQL for invalid input"
3. No database dependency during evaluation

## Sub-scores

| Sub-score | Description |
|-----------|-------------|
| `semantic_equivalence` | Do both queries return same data? |
| `syntax_correctness` | Is SQL syntax valid? |

## Implementation

- Uses Langfuse prompt manager for prompt
- Prompt template: `evaluation_sql_judge`
- Model: GPT-4o (configured in settings.yaml)
